# 交通シミュレーション導入に関する未解決の疑問点

本ドキュメントは、`FutureWork.md §7`（交通シミュレーション導入）の提案に対して、技術的・設計的観点から洗い出した疑問点と、その疑問が生じる理由を整理したものである。

関連ドキュメント:
- [FutureWork.md §7](../FutureWork.md) — 改善案の概要
- [TrafficNetwork.md](./TrafficNetwork.md) — 現状の道路データ構造の分析

## 1. FutureWork記述の正確性に関する疑問

### Q1-1: 「LOD3でなければ交通シミュレーション不可」は正確か？

**疑問の理由:**
FutureWorkでは「PLATEAUのToolkitが提供する交通シミュレーション機能はLOD3前提」と記載しているが、これは**PLATEAU Sandbox Toolkitに限定した話**である。PLATEAU公式ツール群には以下のように、LOD1からネットワークを生成できるツールが存在する:

| ツール | LOD1対応 | 出力 |
|--------|----------|------|
| [PLATEAU-RoadNetwork-Generator](https://github.com/Project-PLATEAU/PLATEAU-RoadNetwork-Generator) | **対応** | Shapefile / GeoJSON（ノード・リンクデータ） |
| [Auto-Create-tran-lod1-2-tool](https://github.com/Project-PLATEAU/Auto-Create-tran-lod1-2-tool) | **入力がLOD1** | LOD1→LOD2への自動変換 |
| PLATEAU SDK for Unity v3.2 道路ネットワーク機能 | **LOD1/2/3対応** | Unity内で道路ネットワーク生成 |
| Sandbox Toolkit 交通シミュレーション | LOD3のみ | 車両自動走行 |

→ **FutureWorkの記述を修正し、LOD1から道路ネットワークを生成できるツールの存在を明記すべき。** 特に`PLATEAU-RoadNetwork-Generator`はFutureWork案Bで提案している「スケルトン化→交差点ノード→車線推定」のアプローチを既に実装している可能性があり、**車輪の再発明を回避できる**。

### Q1-2: 浪江町にPLATEAUデータは存在するか？

**疑問の理由:**
PLATEAUオープンデータポータルで確認すると、福島県内のPLATEAU対応都市は限定的:

| 自治体 | データ年度 | 道路LOD |
|--------|-----------|---------|
| いわき市 | 2020年 | LOD1のみ |
| 南相馬市 | 2022年 | LOD1が主 |
| 浪江町 | **データなし** | — |

→ FutureWorkでは浪江町をシミュレーション対象地域として挙げているが、**PLATEAUの3D都市モデル自体が浪江町には提供されていない可能性がある**。この制約は明記すべき。

### Q1-3: 国土数値情報に車線数・幅員は本当に含まれるか？

**疑問の理由:**
FutureWork案Aで「道路種別・車線数・幅員情報を含む場合がある」と記載しているが、実際の国土数値情報の道路データ（N01）の属性を確認すると:

- **含まれる属性**: 道路種別コード、路線名、線名、通称
- **含まれない属性**: 車線数、幅員、一方通行

→ 「場合がある」という曖昧な表現は**誤解を招く**。基本的に車線数・幅員は含まれない。代替として、国土地理院の基盤地図情報の道路中心線＋道路縁データから幅員を推定する手法の方が現実的。

## 2. 案A（外部データ紐づけ）の技術的疑問

### Q2-1: PLATEAUとOSMの座標系変換は正確に再現できるか？

**疑問の理由:**
座標変換の連鎖が複雑であり、各段階で誤差が蓄積する:

```
OSM (WGS84 / EPSG:4326)
    ↓ 投影変換（平面直角座標系 例: EPSG:6677）
平面直角座標 (メートル単位)
    ↓ PLATEAU SDKの内部変換（原点オフセット）
Unity ワールド座標
```

予想される誤差の内訳:

| 要因 | 誤差幅 |
|------|--------|
| WGS84 → JGD2011 の測地系差 | 約0.3〜0.5m |
| OSMの道路位置精度（衛星画像トレース品質） | 2〜10m |
| PLATEAU LOD1 ポリゴンの位置精度 | 1〜3m |
| **合計** | **約3〜15m** |

道路幅が6〜12m（市町村道〜国道）であることを考えると、3〜15mの誤差は**隣の道路と混同しうるレベル**。さらに、PLATEAU SDKがインポート時に使用する原点座標（基準点）を外部から正確に取得するAPIが存在するかが不明。

### Q2-2: 福島県農村部のOSMデータ品質は十分か？

**疑問の理由:**
OSMは仕様上、車線数・一方通行・速度制限・交差点接続情報を保持可能だが、これは**仕様上の能力**であり、**実データの充実度**とは別問題。日本のOSMデータは都市部と農村部で完全性に大きな差がある。福島県沿岸部（特に浪江町周辺）は被災地域であり:

- 市町村道レベルの網羅率が不十分な可能性
- 車線数・速度制限等の属性が入力されていない道路が大半の可能性
- 震災後の復興整備で道路状況が大きく変わっており、OSMへの反映が遅れている可能性

→ FutureWorkでは「OSMは車線数・一方通行・速度制限情報を保持」と書いているが、いわき市・浪江町・南相馬市の**実際のOSMデータの充実度を事前調査**する必要がある。

### Q2-3: PLATEAUにあってOSMにない道路（またはその逆）はどう扱うか？

**疑問の理由:**
PLATEAUのデータとOSMのデータは更新タイミングが異なる。特に福島県沿岸部は震災後の復興整備で道路の新設・改修が多く、**片方にしか存在しない道路**が必ず発生する。

考えられる対処パターン:
1. OSMにあるがPLATEAUにない → グラフ上の「見えない道路」として扱う（案Cとの折衷）
2. PLATEAUにあるがOSMにない → 仮想的なノード/エッジとしてグラフに挿入
3. 両方にあるが位置がズレている → バッファリングマッチング

→ マッチング失敗時のフォールバック戦略が未定義。

### Q2-4: FutureWorkで言及している「osm2unity」は実在するか？

**疑問の理由:**
FutureWork案Aで言及されている`osm2unity`というツールの具体的なリファレンスが不明。存在するのは個人プロジェクト（`osm-unity`, `OpenStreetMap-Unity`等）で、**プロダクション品質のツールではない可能性**がある。

→ 現実的には、Pythonの`osmnx`ライブラリでOSMデータを前処理し、GeoJSON形式でエクスポートしてからUnityに取り込むパイプラインの方が確実。

## 3. 案B（LOD1からの自動生成）の技術的疑問

### Q3-1: PLATEAU-RoadNetwork-GeneratorのLOD1出力品質はどの程度か？

**疑問の理由:**
案Bで提案している「スケルトン化→交差点ノード→車線推定」のアプローチは、PLATEAU公式の`PLATEAU-RoadNetwork-Generator`が既に実装している可能性がある。自前実装の前に、このツールの出力品質（特に交差点接続の成功率、生成されるネットワークのトポロジ的正確さ）を評価すべき。

→ **自前実装を始める前に、まず既存ツールの評価が必要。** エラー率や交差点接続の成功率に関する公開情報は現時点で見当たらない。

### Q3-2: ポリゴンスケルトン化のアルゴリズムはどれが適切か？

**疑問の理由:**
LOD1道路ポリゴンは「きれいな矩形」ではなく、不規則な多角形の集合体。スケルトン化アルゴリズムにはそれぞれ弱点がある:

| アルゴリズム | 長所 | 短所 |
|---|---|---|
| Straight Skeleton | 理論的に正確 | 不規則形状で破綻しやすい |
| Medial Axis Transform | 広く実装されている | 細い突起に不要な分岐が大量発生 |
| Thinning (Zhang-Suen) | 実装が容易 | ラスタ解像度依存、高解像度でメモリ爆発 |
| Voronoiベース | 最もロバスト | 後処理（枝刈り）が必要 |

→ どのアルゴリズムを採用しても交差点周辺で問題が発生する。**完全自動化は困難であり、半自動（自動生成→人手補正）のワークフローが現実的**だが、プロジェクトの方針として許容されるか？

### Q3-3: 道路ポリゴン数が膨大な場合、全頂点の近接判定は現実的か？

**疑問の理由:**
隣接ポリゴンの発見には、全`tran_`オブジェクトのメッシュ頂点を取得し、近接頂点を見つける処理が必要。`RoadSnapper.cs`の実装からメッシュ頂点へのアクセスは確立されているが、道路ポリゴンが数千〜数万件の場合、全頂点の近接判定のパフォーマンスが許容範囲かは未検証。

→ 現在のシーン内の`tran_`オブジェクト総数（`GeoSpatialIndex`のBake結果の`roadCount`）を確認し、処理規模を見積もる必要がある。

## 4. 案C（抽象化モデル）の設計疑問

### Q4-1: 「渋滞レベル3/5」はLLMエージェントにとって十分な情報か？

**疑問の理由:**
現在のLLMペイロード（`LLMEvacDecisionRequest`）には、避難所候補の`distance_meters`や`walking_time_minutes`など**具体的な数値**が含まれている。LLMエージェントはこれらの数値を基に意思決定を行っている。交通情報だけ抽象的なレベル表記にすると、**情報の解像度に不整合**が生じる。

「渋滞レベル3/5」では以下が不明:
- それが「5分遅延」なのか「30分遅延」なのか「通行不能」なのか
- どの道路が渋滞しているのか（移動経路上とは限らない）
- 渋滞が増加傾向なのか解消傾向なのか

→ 最低限必要な情報として、**経路ごとの予想所要時間（渋滞考慮）とボトルネック箇所の特定**が必要。以下のようなペイロード構造が考えられる:

```csharp
public class TrafficContextPayload
{
    public RouteTrafficInfo[] route_traffic;     // 各避難所候補への経路の交通状況
    public float local_vehicle_density;          // 周辺の車両密度
    public string local_traffic_description;     // 自然言語での状況説明
    public string[] blocked_roads;               // 通行不能な道路名
}

public class RouteTrafficInfo
{
    public string shelter_id;                    // 避難所ID
    public float estimated_drive_time_min;       // 渋滞考慮の予想所要時間
    public float normal_drive_time_min;          // 通常時の所要時間
    public float delay_ratio;                    // 遅延倍率（2.0 = 通常の2倍）
    public string bottleneck_description;        // "国道6号交差点付近で渋滞"
}
```

### Q4-2: 渋滞レベルの算出根拠は何か？

**疑問の理由:**
「避難者密度から動的に渋滞レベルを計算する」としても、その変換関数（密度→渋滞レベル）のパラメータは何に基づくのか。実データ（実際の避難時交通データ）が入手困難な場合、パラメータの妥当性を検証できない。

現在の`EnvironmentalContextProvider`は静的なBakeデータの検索のみで、**動的な状態（時間変化する渋滞）を管理する仕組みがない**。`nearby_evacuees_density`（`LLMActionMessages.cs`）は単純な100m²あたりの人数であり、道路区間別の密度ではない。

→ 動的な交通状態管理の仕組みと、パラメータの根拠（例: BPR関数の使用）を明確にする必要がある。

### Q4-3: 車両が視覚的に存在しない状態で「渋滞」と伝える妥当性は？

**疑問の理由:**
案Cでは交通ネットワークを完全に再現せず統計的モデルとして渋滞を表現するため、シーン上に車両オブジェクトが表示されない。しかしLLMには「渋滞している」というコンテキストが渡される。

この乖離は:
- シミュレーション結果の**再現性・説明性**に影響する（「なぜ渋滞しているか」が視覚的に確認できない）
- シミュレーション結果を他者（防災専門家等）に**プレゼンテーション**する際に説得力が低い
- 研究論文として成果を公表する際、**査読者から手法の妥当性を問われる**可能性がある

→ 抽象化モデルでも最低限の視覚的表現（道路の色分け等）が必要か検討すべき。

## 5. アーキテクチャ統合に関する疑問

### Q5-1: NavMeshと交通ネットワークはどう共存するか？

**疑問の理由:**
現在の全避難者（`Evacuee.cs`）はNavMeshAgentで移動し、`FireTruckAgent`も同様。NavMeshは「歩行可能領域」として一枚のメッシュ上で経路計算を行い、道路・歩道・広場の区別がない。

車両避難者を導入する場合、2つの選択肢がある:
1. **交通ネットワークグラフ上で移動** → NavMeshとは全く異なる経路探索システムが並存し、相互作用の設計が複雑（例: 車から降りて徒歩に切り替える場面のハンドオフ）
2. **NavMesh上で速度パラメータだけ変更** → 車両が歩道や建物間の隙間を通る非現実的な挙動になる

→ どちらを選択するかで、アーキテクチャへの影響が根本的に異なる。

### Q5-2: Evacuee.csに車両アクションをどう組み込むか？

**疑問の理由:**
現在の`ActionType`列挙型は`EVACUATE`, `STAY`, `SEARCH_FAMILY`, `CONTACT`, `FOLLOW`, `TALK`の6種。LLMが「車で避難する」「徒歩に切り替える」という判断を返した場合、以下のような新しいアクションが必要になる:
- `DRIVE` — 車両で避難所へ移動
- `ABANDON_VEHICLE` — 車を放棄して徒歩に切り替え

`Evacuee.cs`は既に4700行以上あり`NavMeshAgent`との結合が深い。車両移動と歩行移動を同一クラスで管理するのか、`VehicleEvacuee`等の別クラスを新設するのかの判断が必要。

### Q5-3: 500エージェント + 交通シミュレーションのパフォーマンスは許容範囲か？

**疑問の理由:**
現在のシステムでは:
- 500体のLLMエージェントが各ステップでWebSocket経由でLLM APIを呼び出している
- 建物・道路データはグリッドベースの空間インデックスで`O(1)`に近い検索を実現

交通シミュレーションが追加されると:
- グラフ上の経路探索（ダイクストラ等）を全エージェントが実行する必要がある
- 「各道路区間にいる車両数」のリアルタイム集計が必要（現在のポイント検索とは異なるエッジベースのデータ構造が必要）
- 渋滞の動的更新と伝播計算

→ NavMeshの経路計算はUnityの内部で最適化されているが、独自のグラフ探索は自前実装になり、500エージェント×毎フレームのコストが懸念される。

### Q5-4: 外部データのインポートは既存のBakeパイプラインにどう統合するか？

**疑問の理由:**
現在の`GeoSpatialIndexBaker`は完全にUnityエディタ内で完結しており、外部データ（OSM等）のインポートパイプラインは存在しない。OSMデータを取り込む場合:
- Bake時（エディタ拡張）で行うのか、ランタイムで行うのか
- `GeoSpatialIndex`のスキーマ変更は既存のBakeデータ（`.asset`ファイル）との後方互換性を破壊する可能性がある
- Pythonで前処理（`osmnx`等）し、GeoJSONをUnityに取り込むパイプラインの場合、ビルドプロセスが複雑化する

### Q5-5: 時間スケールの整合性はどう保つか？

**疑問の理由:**
現在のシステムは`EnvManager.AccSimulateScale`による時間加速と`Update()`ベースの可変フレームレートで動作している。交通シミュレーションは通常、固定タイムステップ（例: 1秒刻み）で計算する。

→ 時間加速時に交通シミュレーションも同期して加速させる仕組みが必要。`FixedUpdate()`での実装なのか、独立したタイムステップ管理なのか未定義。

## 6. 要件の欠落

### Q6-1: 車両避難者と徒歩避難者の比率・判断基準は？

**疑問の理由:**
交通シミュレーションの前提として「誰が車で避難するか」が必要だが、以下が全て未定義:
- 避難者のうち何%が車で避難するかの設定パラメータ
- 「いつ車で避難するか」の判断ロジック（ペルソナ属性？ LLM判断？ ルールベース？）
- 現在のペルソナデータ（`persona_maker.py`）に車両保有情報が含まれていない
- 家族構成（高齢者・幼児の同行）が車両選択に与える影響

→ 東日本大震災の避難実態調査では、自動車での避難割合が非常に高かった（地域によっては80%超）。このデータを根拠にパラメータを設定する必要がある。

### Q6-2: 駐車場・車両の配置はどうするか？

**疑問の理由:**
避難者が車にアクセスするまでのプロセスが未定義:
- 自宅の駐車場まで歩く時間
- 車に乗り込む時間
- 車両オブジェクト自体のシーン内配置方法
- 車両台数の上限や相乗り避難の仕組み

### Q6-3: 災害による道路損壊・閉塞はどう表現するか？

**疑問の理由:**
交通シミュレーションの価値は「災害時の非日常的な交通状況」の再現にある。以下のシナリオへの対応が未定義:
- 地震による道路損壊、がれきによる通行止め
- 液状化による道路陥没
- 津波到達による通行不可（`DisasterEventManager`からの通知で発火可能だが、交通ネットワーク上での反映方法が未定義）
- 橋梁の損壊（`sectionType=3`は橋梁を示すデータが既にある）による孤立地域の発生

### Q6-4: 車両放棄と移動手段の切り替えはどう実装するか？

**疑問の理由:**
渋滞に巻き込まれた車両避難者が車を放棄して徒歩に切り替えるシナリオは、東日本大震災で実際に多数発生した。実装には以下が必要:
- 交通ネットワーク上の位置 → NavMesh上の位置へのハンドオフ処理
- LLMに「車を放棄すべきか」の判断をさせるためのコンテキスト設計
- 放棄された車両が道路を塞ぐ二次的渋滞の再現

### Q6-5: 交通シミュレーションの検証方法は？

**疑問の理由:**
シミュレーション結果の妥当性を検証する指標が未定義。検証には段階がある:

1. **定性的検証（最低限必要）**: 防災専門家に渋滞パターンが直感に合うか確認
2. **既存データとの比較（推奨）**: 東日本大震災時の車両プローブデータ（Honda/Toyotaが提供した走行実績データ）との比較
3. **モデル間比較（理想）**: SUMO等の本格的交通シミュレータとの比較

→ 最も重要な問い: **「交通情報の精度がLLMエージェントの意思決定の質にどの程度影響するか」を測定する仕組みを用意できるか？** 渋滞情報なし / 3段階 / 5段階＋ボトルネック情報 の条件比較が有効。

## 7. 戦略的な疑問

### Q7-1: 完全な車両シミュレーションは本当に必要か？

**疑問の理由:**
このシミュレーションの主眼はLLMエージェントの**避難意思決定**であり、車両のレーン変更や信号制御の忠実さではない。車両は「エージェントの意思決定に影響を与える環境要因」として機能すれば十分な可能性がある。

精密な車両シミュレーション（SUMO等）は大量のパラメータ（信号タイミング、車種別加速度、車間距離分布等）を必要とし、入手・検証が困難。見かけ上は精密だが**根拠の薄いシミュレーション**になるリスクがある。

→ BPR関数ベースの簡易モデル（グラフの各エッジに交通量→旅行時間の関数を適用）で十分かもしれない。

### Q7-2: 案Cの最小実装を先行すべきではないか？

**疑問の理由:**
**交通情報の精度向上にかけるコストと、LLMの意思決定品質向上の関係は線形ではない可能性がある。** つまり、簡易な渋滞情報でもLLMの行動が大きく変わる可能性がある一方、精密な交通シミュレーションに投資しても意思決定の質がほとんど変わらない可能性もある。

推奨される段階的アプローチ:
1. **Phase 1**: 案Cの最小実装（`RoadEntry`への混雑度追加 + LLMペイロードへの`TrafficContextPayload`追加）
2. **Phase 2**: Phase 1の結果を分析し、交通情報がLLMの意思決定に与える影響を計測
3. **Phase 3**: 影響が大きければ案A+Cハイブリッドに投資、小さければ案Cの精緻化で十分

→ まず最小限の交通情報でLLMの反応を見てから、精緻化の方向を決定すべき。

### Q7-3: 案A+Cのハイブリッドが最も費用対効果が高いのでは？

**疑問の理由:**
各案を組み合わせることで、それぞれの弱点を補完できる:

```
【データレイヤー】
  OSM → 道路ネットワークグラフ（ノード・エッジ）……案A
       ↕ Bake時にマッチング（半自動）
  PLATEAU LOD1 tran_ → 視覚的表現（既存のまま）

【シミュレーションレイヤー】
  グラフ上でBPR関数ベースの交通流計算 ……案C
       ↓
  各エッジの混雑度をリアルタイム更新

【情報伝達レイヤー】
  EnvironmentalContextProvider.GetTrafficContext()
       ↓
  LLMEvacDecisionRequest.traffic_context に格納
```

このアプローチのメリット:
- PLATEAUの道路メッシュには一切手を加えない
- スケルトン化の困難さを回避（OSMからグラフ取得）
- 案Bのリスク（ポリゴンスケルトン化の品質問題）を回避
- 簡易モデルで開始し、後から精緻化可能

最大のリスクはPhase 2のマッチング精度。失敗した場合は案C単独に縮退する。
